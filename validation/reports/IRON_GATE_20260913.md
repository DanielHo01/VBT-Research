### 3.2 本轮修掉的 3 个真 bug

#### Bug 1 — C++ 置信度双重 sigmoid（弯路一在 C++ 端复活）· 致命

`best.onnx` 输出 `[1,5,8400]`，`row[4]` **已是概率**（实测首帧 min=0.000000 max=0.930283 mean=0.002112）。
C++ 却再套一层 sigmoid，把概率压进 [0.5, 0.731]，`conf_thresh=0.40` 完全失效：

| | 正确解析 | 旧 C++（双 sigmoid） |
| --- | --- | --- |
| 过阈值 anchor 数 | 20 | **8400 / 8400** |

max-area 于是锁定到无意义巨框，后果：

| 量 | 修复前 | 修复后 | Python |
| --- | --- | --- | --- |
| mpp | 0.000565539 | **0.00246996** | 0.002471 |
| y_range | 0.259874 m | **0.66423 m** | 0.664 m |
| status | NO_CLEAN_SEGMENT | **OK** | OK |
| MCV | [] | **[0.701, 0.753]** | [0.705, 0.762] |

> 注：此 bug 的症状（mpp 虚小 4.37×）与交接文档「弯路六 Letterbox 反变换」几乎一致，
> 但**根因不同** —— letterbox 逆变换本身是对的，错的是置信度解析。
> Python 端早已修复并写进 docstring，C++ 端此前未同步。

#### Bug 2 — C++ DenseVisualTracker 与 Python 是两套架构

旧 C++ 实现：
- `step_interframe` **完全不跑光流**，直接把上一帧 y/v 原样返回（速度呈阶梯保持）；
- `step_keyframe` 用「两关键帧差分」算速度，构造的 Kalman **从未参与输出**。

Python 实现：物理空间 CA 卡尔曼（`[y(m), v(m/s), a(m/s²)]`）+ 每帧 LK 光流观测 + 关键帧 YOLO 校正。

已按 Python 语义重写 `PhysicalKalman`，数值逐项对齐（`P0=diag(0.001,0.1,1.0)`、
`q_a=25.0`、`R=0.0004`、dt 取真实 PTS 差），特征点与 LK 参数全部对齐。

#### Bug 3 — C++ 解析层多了出画过滤

Python `PlateDetector.detect` 不做出画剔除，C++ 多了 `orig.cx<0 || orig.cx>=orig_w …`，
改变了 `max-area` 选框结果。出画拒绝属「锚定打分」层策略，不应混在解析层，已移除。

### 3.4 判据修正说明：PCV → MCV

旧 golden_test 以 **PCV（向心段单帧峰值速度）** 判定，容差 0.001 m/s。这是错误的尺子：

1. PCV 是整条轨迹里**噪声最大的单个采样点**，Python(float64/NumPy) 与
   C++(float32 ONNX + 不同 LK 实现) 的单帧微差会被峰值算子直接放大；
2. **PCV 不是产品指标** —— GymAware 真值、App 展示、34 视频标注给的全是 MCV；
3. 实测：34/34 status 一致、31/34 计数一致、MCV 中位偏差 0.004，
   但按 PCV 判定只有 1/34 —— 会把一个已对齐的引擎误判为全盘失败。

现改为 **MCV 为硬判据（≤0.005 m/s）**，PCV 与 mpp 相对偏差降为诊断量输出。

### 3.5 为何仍差 3 条：本沙箱的不可约误差源

**Python 用 OpenCV 5.0.0（PyPI wheel），C++ 用 OpenCV 4.10.0（源码自建）。**

`goodFeaturesToTrack`（Shi-Tomasi 角点）与 `calcOpticalFlowPyrLK` 的实现在 OpenCV
4→5 之间有差异，两端选出的特征点集合不同 → LK 位移观测序列不同 → Kalman 轨迹
微分叉 → 分段边界偶尔差 1–2 帧 → MCV 偏差 0.01–0.03。

这解释了残差的形态：**偏差集中在 0.005–0.03 这个「小但非零」的区间**（28/34 ≤0.02），
而非随机大偏差；且 mpp（不经光流）两端一致到 1e-6。

> 本沙箱 apt 不可用，无法安装与 Python 端同版本的 OpenCV 5 C++ 库。
> **在用户 WSL2 环境上两端使用同版本 OpenCV，预计可直接跨过 20/34。**
